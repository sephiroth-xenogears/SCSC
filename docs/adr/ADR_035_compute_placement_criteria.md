# ADR 035 — 演算配置の切り分け基準

**状態**: 確定（2026-09-19）
**関連**: ADR 024, 025, 028, 030, 033, 034

---

## 1. 背景と目的

SCSC の三層アーキテクチャ（大脳＝Jetson AGX Orin / 小脳＝RA8M2 Cortex-M85 /
脳幹＝RA8M2 Cortex-M33）における「どの処理をどの石に置くか」の判断は、
これまで個別の ADR（024, 025, 028, 030）に**結果だけ**が記録され、
その判断を導いた**基準は明文化されていなかった**。

本 ADR は、過去の判断事例から基準を逆算し、石に依存しない形で定義する。

**目的は2つ。**

1. 新しい処理が増えたとき、同じ基準で配置を決められるようにする
2. 大脳側のハードウェアが変わっても（Orin → Thor → X199 など）、
   配置を同じ基準で決め直せるようにする

---

## 2. 四つの軸

### 軸1 — デッドライン（拒否権を持つ）

**問い**: 何ms以内に終わらなければ、その処理結果は無効になるか。
取りこぼしたとき、値は失われるか。

この軸は**他の軸に対して拒否権を持つ**。他の軸がどれだけ大脳側に有利でも、
デッドラインが 1kHz 級なら機体側に置くしかない。
非決定的な経路（無線・リッチOS・ベストエフォート通信）をまたがせない。

判定の下位ルール:
- **1ms 以内に閉じる必要がある処理は、機体側（M85）で完結させる**
- **取りこぼしが致命的なデータ取得は、ポーリングではなく割り込み＋DMA**
  （ポーリングは周期の隙間で欠測を生む）

### 軸2 — 資源量（演算量・メモリ量）

**問い**: 必要な演算量とメモリ量が、その石の身の丈に収まるか。

M85 側の実際の上限: 内蔵 SRAM 2MB（CM85 TCM 256KB / CM33 TCM 128KB 含む）、
コード用 MRAM 最大 1MB、外付け Flash なし（ADR 030）。
Jetson 側: 64GB ユニファイドメモリ、GPU。

収まらなければ、**軸1が許す限り**大脳側へ移す。

### 軸3 — データ発生源への近さ

**問い**: そのデータはどこで生まれるか。手元で処理すれば、
運ぶ量も運ぶ時間も減らせるか。

センサに近い側で処理すれば、通信帯域と遅延を節約できる。
ただし**軸2で弾かれた場合は諦めて運ぶ**。

### 軸4 — 故障時の振る舞い

**問い**: 上位層が落ちたとき、機体の姿勢を誰が保つか。
その処理は上位から独立して動けるか。

この軸で機体側に残すと決めた処理は、
**上位（Jetson、無線リンク）の生死に依存してはならない**。

> **注記**: 軸4は過去の判断で明示的には使われていなかった。ただし
> 「起動シーケンスを M85 に置く」「リンク断を異常でなく想定状態として扱う」
> （ADR 028）「脳幹 M33 を電気的に分離する」といった判断は、
> 実質的にこの軸が働いた結果である。2026-09-19 に初めて言語化された。

## 3. 適用順序

```
軸1（デッドライン）で置ける場所を絞る    ← 拒否権。ここで決まれば以降は検討不要
   ↓
軸2（資源量）で身の丈を確認              ← 収まらなければ移す
   ↓
軸3（近さ）で近いほうを選ぶ              ← 軸1・軸2が許す範囲で
   ↓
軸4（故障時）で最低限残すものを決める    ← 上位非依存で動く必要があるもの
```

## 4. 既存 ADR との照合（検証）

| 判断 | 該当ADR | 決め手 | 整合 |
|---|---|---|---|
| 1kHz反射（IMU/FSR）を M85 | 024 | 軸1 | ✅ |
| 100–200Hz 姿勢推定（EKF）を M85 | 024, 028 | 軸1（＋軸3） | ✅ |
| センサ取得を割り込み＋DMAダブルバッファ | — | 軸1（取りこぼし） | ✅ |
| 20軸ICSを5本並列バスで M85 駆動 | 025 | 軸1 | ✅ |
| サーボ指令生成を M85 | 025 | 軸1 | ✅ |
| 起動シーケンスを M85 | — | **軸4** | ✅（今回言語化） |
| 疎指令→密制御の補間を M85 | 028 | 軸1 | ✅ |
| リンク断フォールバックを M85 | 028 | **軸4** | ✅（今回言語化） |
| カメラ画像処理を Jetson | 028 | 軸2 が軸3 に勝った | ✅ |
| 行動経路決定（SLAM）を Jetson | 028 | 軸2 | ✅ |
| 目標姿勢・経路の指令を Jetson | 028 | 軸2（軸1が緩い） | ✅ |
| ログを Jetson | 030 | 軸2（メモリ） | ✅ |
| ESKF 共分散更新の Jetson 移設を撤回 | 033 | **軸1の拒否権** | ✅ |

**全13件が4軸で説明できた。** 特に:

- **カメラ**は軸3（発生源は機体側）と軸2（M85には重すぎる）が競合し、軸2が勝った例。
  軸間の優劣が実際に問われた唯一の事例。
- **ADR 033 の E案撤回**は、軸1の拒否権が後から効いた例。
  当初は軸2（FP64 が M85 で高コスト）だけを見て Jetson 移設を検討したが、
  軸1がそれを許さなかった。**適用順序を守っていれば最初から弾けた判断**。

---

## 5. 適用範囲外

本 ADR は**処理の配置**を決める基準であり、**石そのものの選定**は対象外。

石の選定には別の観点が効く（エコシステムの成熟度、移行コスト、供給期間、
価格、実績）。ADR 034（AMD Kria 不採用）はこちらに属し、本 ADR の4軸では
説明できない。石の選定基準は別 ADR として立てること。

## 6. 未確定・今後埋める欄

本 ADR は**基準**であり、閾値の数字は実測で埋める。机上で決めない（RHPC原則6）。

| 項目 | 状態 | 埋め方 |
|---|---|---|
| ICS 1軸あたりの往復時間 | **未実測** | Nano R4 で実測 → 20軸に外挿 → 必要バス本数を確定 |
| 1kHzループ内の時間予算配分 | **未確定** | 実測後に「反射に何µs、ICSに何µs」を割り付ける |
| M85 のバス調停 最悪レイテンシ | **未実測** | DWT サイクルカウンタで DTC 有/無の差分を測る |
| EKF の実行時間（M85上） | **未実測** | 24次元想定で約10万FLOP/ステップ。実機で確認 |
| M85 側コードサイズ | **未確定** | 1MB MRAM に収まるか（ADR 030 の前提） |

## 7. 今後の運用

- 新しい処理の配置を決めるときは、§3 の順序で4軸を通す
- 判断結果だけでなく、**どの軸が決め手になったか**を個別 ADR に記録する
- 軸同士が競合した場合（カメラの例）は、どちらが勝ったかとその理由を残す
- 4軸で説明できない判断が出てきたら、**第5の軸が隠れている可能性**を疑う
