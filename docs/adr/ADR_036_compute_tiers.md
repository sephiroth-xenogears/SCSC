# ADR 036 — 計算階層の三層化（機体／エッジ HPC／バックエンド HPC）

**状態**: 確定（2026-10-08）
**関連**: ADR 024, 028, 030, 033, 034, 035

> 番号について：2026-09-29 に `inv3_spd_core` の配列渡しリファクタを「ADR 036 案」として提示している。
> そちらをすでに ADR 036 として採番済みなら、本 ADR は 037 に読み替えること。

---

## 1. 背景

ロボットの科学技術計算を数値計算で解きまくる構想について、
「Jetson AGX Orin を並べて FP32 で解く」案と「Strix Halo（Ryzen AI Max+ 395）を並べる」案の
間で迷いが生じた。

検討の結果、迷いの原因は石の優劣ではなく、**要求の異なる2種類の計算が1つの構想に混在していた**
ことだと分かった。YK の整理は次のとおり。

- **エッジ側（ロボティクス制御本体）** は「組込み機で HPC をやる」
- **それ以外の科学技術計算やロボットの高位計算処理** は「手の届く汎用品で HPC をやる」

ただしこの二分では、Jetson が担う知覚・経路計画（数十 ms で答えを返す処理）がどちらに入るか
曖昧になる。そこで階層を三層に分けて境界を定義する。

---

## 2. 決定：三層の計算階層

| 層 | 担う処理 | 締め切り | 石（現行） | 哲学 |
|---|---|---|---|---|
| **機体** | 1kHz 反射、ESKF、サーボ駆動、起動シーケンス、リンク断フォールバック | ms（ハードリアルタイム） | RA8M2（M85／M33） | 組込み |
| **エッジ HPC** | 知覚（カメラ）、SLAM のフロントエンド、経路計画、目標姿勢の生成、ログ収集 | 数十 ms（ソフトリアルタイム） | Jetson AGX Orin | 組込み HPC |
| **バックエンド HPC** | 慣性パラメータ同定、歩容の軌道最適化、地図の大域最適化、安定性解析、振動解析 | なし（オフライン） | 未定（当面は Orin の CPU や手元の Linux PC） | 汎用品 HPC |

---

## 3. 境界の引き方（ADR 035 の4軸を適用）

### 機体 ↔ エッジ HPC
- **軸1（デッドライン）**：1ms 以内に閉じる必要がある処理は機体（ADR 024, 028）
- **軸4（故障時の振る舞い）**：エッジや無線リンクが落ちても姿勢を保つ処理は機体

### エッジ HPC ↔ バックエンド HPC
- **軸1（デッドライン）**：数十 ms で答えが要る処理はエッジ、締め切りのない処理はバックエンド
- **軸3（データ発生源への近さ）**：生画像など帯域の大きいデータを扱う処理はエッジ

### 同じ処理が層をまたいで分かれる例

| 処理 | エッジ HPC 側 | バックエンド HPC 側 |
|---|---|---|
| SLAM | 毎フレームの自己位置推定 | 地図全体の大域最適化（FP64 が欲しい部分） |
| 軌道 | オンラインの再計画 | 歩容ライブラリの事前生成（直接コロケーション） |
| モデル | 同定済みパラメータを使う | パラメータを同定する（悪条件な最小二乗） |

### 動力学の配置（2026-10-08 追記）

動力学は特定の層に属する処理ではなく、**複数の層で使われる道具**である。
置き場所は、動力学を「誰が使うか」の締め切りで決まる。

| 使い道 | 締め切り | 精度 | 層 |
|---|---|---|---|
| 重力補償、ZMP の計算（倒立振子などの簡略モデル） | 1ms | FP32 | **機体** |
| 全身制御、MPC のロールアウト（短い先読みを多数並列に回す） | 数 ms〜数十 ms | FP32 | **エッジ HPC** |
| 検証用シミュレーション、歩容の軌道最適化、パラメータ同定、ロバスト性のモンテカルロ試験 | なし | FP64 が望ましい | **バックエンド HPC** |

- **シミュレーションはバックエンド**：締め切りがなく（軸1が効かない）、長時間の積分で誤差が
  蓄積するため FP64 が効き、多数の条件を回す処理量の勝負になる
- **MPC のロールアウトはエッジ**：先読みが短く誤差が蓄積しにくいので FP32 で足り、
  制御ループの中にあるためエッジから出せない。SCSC の核である
  「Featherstone の空間ベクトル代数を CUDA で回す」はこの層に属する

### 方針：動力学の式は1か所に書いて全層で共有する

動力学の式は `__host__ __device__` テンプレートとして**唯一の定義箇所**に書き、
精度（`T = float / double`）と実行先（GPU／CPU）だけを層ごとに変える。

- エッジ HPC：GPU・FP32 で制御に使う
- バックエンド HPC：CPU・FP64 でシミュレーションに使う

これにより、**バックエンドの FP64 シミュレーションが、エッジの FP32 制御の物差しになる**。
`inv3_spd_typed.cu` で確立した「CPU の double が GPU の float を検証する」構造
（式は `inv3_spd_core<T>` に一箇所化、検証は常に double）を、システム全体に広げたものである。

エッジとバックエンドで別々の動力学を実装すると、シミュレーションと実機の結果がずれたとき、
原因がモデルの差なのか実装の差なのか切り分けられなくなる。これを構造で防ぐ。

## 4. 層ごとの石の選定基準

ADR 035 §5 で「石そのものの選定は別基準」として先送りにした部分を、層ごとに定める。

### 機体
- 割り込みの決定論（ARM NVIC 等）
- 長期供給と産業グレード
- ペリフェラルの数と質（SCI 多数、DMA/DTC、16bit ADC）
- 低電力・小面積
- FP64 に依存しない設計にする（平方根形式等で精度を稼ぐ）

### エッジ HPC
- 電力と重量（将来の機体搭載を見据える）
- CUDA とロボット向けソフトウェア資産
- センサ I/O（カメラ等）
- **計測の信頼性**（Nsight 等のプロファイラと安定したドライバ）
- FP32／低精度で性能が出ること

### バックエンド HPC
- 解く問題の律速に合わせた**コストあたりの性能**
  - FP64 の演算律速 → CPU の FP64 性能／円
  - 帯域律速 → メモリ帯域／円
  - FP32・混合精度で解ける問題 → GPU の FP32 性能／円
- ノード間通信（クラスタ化する場合）
- **計測の信頼性**（ドライバとランタイムの安定性）
- 汎用品であること（手の届く価格、入手性）

---

## 5. 層間のデータの流れ

```
バックエンド HPC ──（同定済みパラメータ、歩容ライブラリ、地図）──▶ エッジ HPC ──（目標姿勢・経路）──▶ 機体
バックエンド HPC ◀──（ログ、センサ記録）─────────────────── エッジ HPC ◀──（ログ：ADR 030）──── 機体
```

- バックエンド HPC は**リアルタイムのループに入らない**。オフラインで計算した結果を、事前にエッジへ渡す
- エッジ ↔ バックエンドの接続が切れても、ロボットの動作には影響しない（ADR 028 のリンク断の考え方を上位にも適用）

---

## 6. 帰結

1. **「Jetson を並べるか Strix Halo を並べるか」は二者択一ではなくなった。**
   それぞれの層が §4 の基準で石を選ぶ
2. **クラスタ化の議論も層ごとに独立する。**
   - エッジ HPC のクラスタ（Jetson ×N）は低遅延が要件（SCSC Phase 1/2、DPDK・RoCE）
   - バックエンド HPC のクラスタはスループットが要件（パイプライン並列など）
3. **バックエンド HPC は今すぐ石を買わずに始める。**
   当面は Orin の CPU（double）や手元の Linux PC で、2リンクの慣性パラメータ同定などから着手する。
   石の購入は、問題の律速を測ってから §4 に当てはめて決める（RHPC 原則6・原則11）
4. **バックエンド HPC のコードは石に依存しない形で書く。**
   CPU の double 参照実装＋CUDA で書いておけば、HIP（AMD）への移植はほぼ機械的にできる
5. **動力学の式は全層で共有する（§3 参照）。**
   バックエンドの FP64 シミュレーションを、エッジの FP32 制御の物差しとして使う
